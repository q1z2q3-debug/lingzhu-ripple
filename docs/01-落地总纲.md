# 落地总纲：把涟漪认知场装进灵助

> 版本 v1.0 ｜ 面向：能科科技 灵助产品线 / 运维域与质量域实施团队

## 一、为什么是"判断内核"而不是"又一个助手"

灵助（工业软件智能工具集）已经具备知识问答、规则检查、图纸识别、异常诊断、方案推荐等能力，
这些能力在"给建议"这一层是够的。真正卡住落地的是三个问题：

1. **可复核性**——助手说"轴承可能磨损"，工程师凭什么信？依据在哪一条？
2. **经验复用**——上次三号泵的结论，这次能不能直接调用，而不是每次重新"推理"一遍？
3. **不确定性**——什么时候该说"我不确定，请人看"？现在的系统几乎永远给出一个答案。

涟漪认知场对这三个问题给出的是机制，不是话术：

| 问题 | 机制 | 工程表现 |
|---|---|---|
| 可复核 | 每维三态都由具体测点的 `value/unit/score/warn/crit` 推出 | 工单里带"证据链"，逐维可追 |
| 经验复用 | 因果免疫层（同根因 ≥3 次或已核验即固化） | 同类症状 ms 级返回已验证处置 |
| 不确定性 | 场熵 + 驻波比 + 候选分歧度 | 共识强则派单，弥散则转人工 |

因此它的正确位置是：**灵擎之上、灵助各域助手之下的公共判断层**。
运维域的"设备预测维护助手"、质量域的"质量改进助手"，调用的都是同一份内核、同一份因果库。

## 二、四层接入架构

```
┌──────────────────────────────────────────────────────────────┐
│ 业务入口：灵助各域助手（设备预测维护 / 质量改进 / 售后分析 …）      │
│   设计/CAE/EDA/BOM/工艺/报价/调度/库存 等助手亦可复用               │
└───────────────┬──────────────────────────────────────────────┘
                │ 调用 Skills（何时用、怎么解读、何时必须停）
┌───────────────▼──────────────────────────────────────────────┐
│ 灵擎 · Skills 管理 → 多 Agent 配置 → 工作流配置                    │
│   诊断 Agent / 根因追溯 Agent / 态势研判 Agent                     │
└───────────────┬──────────────────────────────────────────────┘
                │ MCP（stdio）
┌───────────────▼──────────────────────────────────────────────┐
│ 涟漪认知场 MCP Server（8 工具）                                   │
│  read_condition · diagnose · immunity_query · counterfactual     │
│  field_status · learn_case · seed_knowledge · evolve             │
└───────────────┬──────────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────┐
│ 认知内核：19683 维概率场 + 因果免疫 + 七层记忆 + 幻觉中和          │
│ 数据：EAM/工单（因果库）· SCADA/PHM（测点）· FMEA/QMS（种子）      │
└──────────────────────────────────────────────────────────────┘
```

要点：**只有"测点 → 三态映射器"这一个主观接口需要客户标定**，其余全部是确定性计算，
换设备只换 profile，不动内核、不改 Agent、不改工作流。

## 三、与灵助现有能力的互补关系（务必对外这样表述）

| 灵助已有 | 涟漪认知场补的 | 关系 |
|---|---|---|
| 知识问答 / 方案推荐（大模型生成） | 判断是否有据、能否派单 | **校验层**，不替代生成 |
| 规则检查（阈值/标准） | 阈值之外的态势与趋势、候选根因排序 | **上游研判层** |
| 异常诊断（告警） | 告警的"确定性"与"经验复用" | **仲裁层** |
| 数据分析 | 反事实沙盘（干预前先演练） | **增强层** |

一句话口径：**大模型负责"想得出"，涟漪负责"想得对、可追、敢不敢用"。**

## 四、数据接入映射（最小可用集）

| 数据源 | 用途 | 最小字段 | 落地方式 |
|---|---|---|---|
| SCADA / PHM / 在线监测 | 实时测点 | 15 个核心测点（见 `docs/03`） | 适配器直连或中间表 |
| EAM / 工单系统 | 因果库、免疫种子 | 症状描述、根因、处置、设备类型、是否核验 | `ripple_seed_knowledge` 批量导入 |
| FMEA / 故障树 | 先验知识 | 失效模式 → 根因 → 措施 | 同上，`verified=true` |
| QMS / 缺陷库 | 质量域根因追溯 | 缺陷类型、工序、批次、供应商 | 质量 profile + 种子 |
| 灵擎知识库 | 文档型补充 | 设备手册、维修规程 | 由 Agent 引用，不进入因果层 |

原则：**因果库只收结构化结论**（症状/根因/处置三元组），文档留给知识库检索。
两者混放会让"免疫"退化成"检索"，失去 ms 级与可核验性。

## 五、指标与验收（对齐灵助募投口径）

| 维度 | 灵助公开目标 | 本包的可测口径 | 验收方式 |
|---|---|---|---|
| 预警准确率 | ≥85% | 免疫命中率 × 匹配度≥0.62 的准确率 | 历史工单回放，混淆矩阵 |
| MTTR | 数小时 → 分钟级 | 从"读数到结论+工单"耗时（实测 ≈12ms，链路含网络与人工确认） | 影子期计时埋点 |
| 工单响应效率 | +60% | 自动生成工单占比 + 人工填写字段减少量 | 影子期统计 |
| 维护成本 | −20%~40% | 误报减少导致的无效出动次数 | 与基线对比 |
| 判断可复核 | —— | 每条结论 100% 带证据链 | 抽查 50 条工单 |

**影子模式（W3）是硬要求**：先只给提示、不派单，比对人工结论，达标后再开派单权限。
这一步不做，任何准确率数字都不可信。

## 六、风险与边界（必须写进合同/评审材料）

1. **标定风险（最高）**：九维压缩规则一偏则全偏。缓解：proﬁle 版本化、变更留痕、上线前回放验证。
2. **数学边界**：本包已补上"可达性 + 唯一稳态"（混合项保证状态空间连通），但**未做收敛速率的解析界**，
   长时演化的收敛时间仍是经验值（实测 200 步内稳定）。
3. **过度自信风险**：已用"先验概率混合（非累加）"封住——观测次数不再抬高置信度，一致性才抬。
4. **责任归属**：派单权限由闸门与人工确认共同持有；`verified=false` 经验只进候选。
5. **叙事风险**：技术包与哲学包分开对外。对客户只讲"判断可复核、经验可复用、不确定性可量化"，
   不讲"数字生命"。两者混谈会让项目在评审会上失分。
6. **算力**：19683 维单步 1.26ms 可接受；若要扩到多设备并流（>500 路），需按设备分片或多进程，
   不要试图用一张场承载全场设备。

## 七、分期（与灵助建设节奏对齐）

- **P0（本包，已交付）**：单设备单域闭环，MCP + Skills + 3 Agent + 2 工作流，11 项自检通过。
- **P1（4–6 周）**：质量域 profile + 跨环节根因追溯（客户投诉→工序→供应商三级链）。
- **P2（8–12 周）**：多设备分片、趋势维预测口径、与灵智（边端推理）下沉。
- **P3**：跨域迁移（设计/工艺/售后），验证"一个内核多域复用"的复用率——这是本方案的经济性来源。
