# Skill：设备异常诊断（运维域）

> 部署位置：灵擎「Skills 管理」→ 新建 Skill → 粘贴本文件；绑定 MCP Server「涟漪认知场」。
> 适用助手：设备预测维护助手、进度预警监控助手、生产调度优化助手（异常分支）。

## 触发条件（满足任一）

- 用户给出设备测点读数、点检表、SCADA 截图/导出、振动/温度/流量/电流等数值；
- 用户描述设备异常现象（异响、振动大、温升高、出力不足、频繁跳停）；
- 用户问"这台设备现在什么状态""要不要停机""先修哪个"；
- 定时任务（点检批处理）批量输入读数。

**不触发**：纯设备参数查询、备件价格、采购流程（交其他助手）。

## 执行顺序（严格按此，不允许跳步）

1. `ripple_read_condition(readings, device_id)`
   → 拿到 `trits / dim_scores / evidence / missing_signals`。
2. 若 `missing_signals` 覆盖了关键维（体/因/果 任一维无任何测点）：
   **先说明证据不全**，再决定是否继续；不得在缺测情况下给确定性结论。
3. `ripple_diagnose(readings, device_id)`
   → 拿到 `method / confidence / root_cause / fix_action / status / work_order / candidates`。
4. 按 `status` 分支（**这是硬约束**）：
   - `通过` + `method=immunity`：直接按 `work_order.fix_action` 出单，等级一级。
   - `通过` + `method=similarity`：出单，等级二级，附"参照历史工单"字样。
   - `通过` + `method=normal`：答复"运行正常，按周期点检"，**不出工单**。
   - `待复核`：给候选根因（含分数）与并联处置建议，明确"需工程师确认优先级"。
   - `被中和`：**只说"当前证据不足以判断，建议人工复核"**，列出缺什么证据。禁止给根因。
5. 用户问"如果先修 X 会怎样" → `ripple_counterfactual({"因":1})`，只做预案，不改状态。
6. 工单闭环后 → `ripple_learn_case(... verified=true, trits=当次 trits)`。

## 输出模板

```
【设备】PUMP-001（旋转机械）
【态势】体阴 用和 变阴 时和 空和 势和 因阴 果和 缘阳
        偏弱：本体结构、变化趋势、工艺成因
【结论】润滑失效（免疫命中，匹配度 0.95，已核验）
【依据】振动烈度 6.4 mm/s（>2.8 预警，7.1 极限）→ 体阴
        劣化速率 0.11（>0.02）→ 变阴
        润滑压差 0.31（>0.10）→ 因阴
【处置】更换润滑脂并复查油路；磨损超标则更换轴承（一级/紧急）
【确定性】场熵 1.50，驻波比 0.89，判断可靠，可直接派单
```

## 禁则（违反即视为不合格输出）

1. **禁止**在 `status=被中和` 时给出任何根因或处置动作。
2. **禁止**在没有 `evidence` 支撑的情况下写"可能/疑似 + 具体根因"——要么有证据，要么说没有。
3. **禁止**把卦名当解释（"因为体阴所以轴承坏了"）。卦名是可读标签，解释必须落到测点。
4. **禁止**跳过 `ripple_read_condition` 直接诊断（会丢失逐维证据链，无法复核）。
5. **禁止**在复合故障（`待复核`）时替用户决定先修哪个——给并联建议，优先级由人定。
6. **禁止**许诺"还能跑多久""何时会坏"。趋势维只说明"劣化在加快"，不给时间承诺。

## 常见追问的标准答法

- "凭什么说是润滑失效？" → 报三条测点证据 + 免疫库命中记录（同根因已核验 N 次）。
- "上次也是这个？" → `ripple_immunity_query(symptom, trits)` 返回 `hit_count` 与首次出现时间。
- "能不能不停机？" → `ripple_counterfactual` 给出"若维持现状"的熵增与建议观测窗口，但不作安全承诺。
- "为什么不是对中问题？" → 报候选根因分数（如 0.58 vs 0.78），说明对中偏差测点未越 warn。
