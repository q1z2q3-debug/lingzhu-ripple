# Skill：质量根因追溯（质量域）

> 适用助手：质量改进助手、售后服务数据分析助手、物料清洗/合规助手（异常分支）。
> 目标：跨环节追溯——"客户投诉生锈 → 防锈工艺参数异常 → 供应商防锈剂批次不合格"这类三级链。

## 触发条件

- 客户投诉、退货、返修、首检不合格、批次性缺陷；
- 用户问"为什么会这样""根因在哪""是供应商还是我们自己的问题"；
- 需要判"要不要扩大排查范围（扩批/回收/停线）"。

## 九维在质量域的落点（必须遵守同一套编码，不许另建体系）

| 维 | 质量域含义 | 示例测点 |
|---|---|---|
| 体 | 产品本体/材料状态 | 膜厚、硬度、粗糙度 |
| 用 | 功能性能 | 密封性、附着力、导电性 |
| 变 | 劣化/漂移趋势 | 参数随批次漂移率 |
| 时 | 时序节奏 | 工序间隔、存放时长 |
| 空 | 位置/装配 | 涂覆位置、夹具定位 |
| 势 | 工艺能力余量 | Cp/Cpk、设备负载 |
| 因 | 工艺成因 | 槽液浓度、温度、时间偏离 |
| 果 | 结果质量 | 缺陷率、一次合格率、客诉率 |
| 缘 | 外部关联 | 供应商批次、来料 PPM、环境湿度 |

## 执行顺序

1. `ripple_read_condition(readings)` —— 用**质量 profile**（`docs/03` 第四节）映射，不用旋转机械 profile。
2. `ripple_diagnose(readings, device_id=<批次号/工单号>)` —— 结论按 `status` 分流（同运维域硬约束）。
3. **跨环节追溯**：对每个候选根因，用 `ripple_immunity_query(symptom, trits)` 查同类历史，
   并逐级向上一环节递推：成品缺陷 → 本厂工序参数 → 来料批次 → 供应商工艺。
   每一级都必须有实测证据，**不允许凭"常见原因"跳级**。
4. 需要判"扩批范围" → `ripple_counterfactual({"因":-1})` 看干预后场是否更清晰
   （更清晰 = 该工艺变量是关键抓手；更模糊 = 证据不足，先别扩批）。
5. 定案后 `ripple_learn_case(verified=true)`，症状与 trits 必须来自同一 mapper。

## 输出模板

```
【追溯链】客诉(生锈) → 防锈槽液浓度偏低(实测 4.1%，下限 5.0%) → 供应商防锈剂批次 B2405 皂基不足
【证据】因果维 −1（槽液浓度偏离 0.31 > 0.10）
        结果维 −1（客诉率 2.1%，基线 0.3%）
        关联维 −1（该供应商近 3 批 PPM 120 → 380）
【确定性】匹配度 0.71，两候选（供应商批次 0.71 / 前处理残留 0.55）分差 0.16 → 待复核
【建议】并联处置：① 供应商批次 8D 追溯 + 换批验证；② 前处理残留复测（碱洗浓度/水洗电导）
        优先级由质量工程师按停线成本确认
【范围】暂不扩批；若复测确认供应商批次，则按批次 B2405 全量围堵
```

## 禁则

1. **禁止**把"设备老化""操作不当""来料波动"当根因——这些是现象归类，不是根因。
   根因必须落到**可处置的对象**：某参数、某批次、某工序、某供应商。
2. **禁止**在 `待复核` 时直接下"停线/回收"结论。停线属高影响动作，必须人工确认。
3. **禁止**为凑因果链编造中间环节（"可能是运输受潮"）而无实测证据。
4. **禁止**混用 profile：质量数据用旋转机械阈值会导致全维"和"，结论必然失真。
5. **禁止**只报一个根因就结案——复合场景必须列候选与分差。

## 与运维域的差别（一句话）

运维域回答"这台机器怎么了、先修哪"；质量域回答"这批货为什么不行、责任在哪一级"。
两者共用内核与因果库，**但 profile 与种子库必须分开**，混库会让免疫命中互相污染。
